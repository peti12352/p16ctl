# Emulation validation

The hardware effect cannot be reproduced without a P16. The ACPI call path can
be validated in a VM, and that is what `scripts/vm-test.sh` does.

## What it runs

- QEMU x86_64 VM.
- Fedora 43 host kernel `7.2.9-100.fc43.x86_64`.
- The real `acpi_call` kernel module, built for that kernel.
- A synthetic SSDT with `\_SB.ATKD.WMNB` and a `LAST` value. The method records
  the mode byte at offset 4, returns 1 for `DEVS`, and returns `0x00010003` for
  `DSTS`.
- A busybox initramfs that writes the exact strings produced by
  `p16ctl performance --dry-run` and
  `p16ctl silent --dry-run`.
- The real `/proc/acpi/call` write and read path.

## Recorded result

```text
=== p16 VM ACPI test ===
DEVS performance result: 0x1called
LAST after performance: 0x1called
DEVS silent result: 0x1called
LAST after silent: 0x2called
DSTS result: 0x10003ed
=== done ===
VM ACPI test passed
```

The `called` suffix is the `acpi_call` result buffer quirk. The checked values
are `LAST after performance: 0x1`, `LAST after silent: 0x2`, and
`DSTS result: 0x10003`.

The script sends a balanced call first and discards its result. On this kernel,
the first `WMNB` call after module load returns a stale `AE_BAD_PARAMETER` while
still executing. The warm-up absorbs that module quirk; the performance and
silent calls are clean. The owner's real P16 script does not show this because
`acpi_call` was already loaded and used by the ASUS stack.

## What this proves

- The exact string generated by `p16ctl` is accepted by the real
  `/proc/acpi/call` interface.
- The 20-byte `DEVS` buffer is parsed as intended.
- The mode byte at offset 4 reaches the ACPI method.
- The synthetic method changes state from 0xAA to 1 for performance and 2 for
  silent.
- The `DSTS` call returns the expected constant.
- The tool's real command strings match the owner's tested recipe, which is
  unit-tested separately.

## What this does not prove

- It does not emulate the ASUS EC, the real `DEVS` AML body, the thermal policy,
  the NVIDIA GPU power budget, or the measured 55 W result.
- It does not prove BIOS 300 behavior.
- It does not replace a P16 A/B/A run.

The missing piece is exactly the hardware behavior. The P16 owner data provides
that: on BIOS 303, the same `DEVS(0x00120075,1)` call produced about 55 W and
1976 MHz versus about 32 W and 1573 MHz in balanced. See
[evidence.md](evidence.md) and [p16-unlock.md](p16-unlock.md).

## Reproduce

```bash
IASL=/path/to/iasl \
KDIR=/path/to/kernel-devel \
sudo ./scripts/vm-test.sh
```

`IASL` and `KDIR` are required. `ACPI_CALL_SRC` can point to a local
`mkottman/acpi_call` checkout; otherwise the script clones it. The host must be
x86_64 with a readable kernel image at `/boot/vmlinuz-$(uname -r)`, a matching
kernel headers tree, QEMU, `cpio`, `gzip`, and a static busybox.

The script needs root only because QEMU with `-acpitable` and the kernel module
build may require it on some hosts. It does not touch the host ACPI namespace.
